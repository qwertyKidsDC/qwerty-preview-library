DNS: record types, caches and troubleshooting
DNS — Domain Name System
A distributed directory that translates names into routing information. A resolver asks authoritative nameservers for answers and caches them.
NS — Name Server
Delegates authority for the domain's DNS zone. It says whom to ask, not where the website itself lives.
A / AAAA
Maps a hostname to an IPv4 / IPv6 address. A wrong address can lead to the wrong host.
CNAME — Canonical Name
Aliases one hostname to another hostname. The www record may be an A record or an alias.
MX — Mail Exchange
Identifies incoming email servers by hostname and priority; the target must itself resolve.
TXT — Text
Stores text used for authentication and other verification, including SPF, DKIM and DMARC.
TTL — Time To Live
How long cached records can be reused. During changes different resolvers may have different answers.

Do it: On DNS Checker query NS then A for the primary domain; then A/CNAME for www and MX for mail. Try a second resolver. Optional terminal commands:

dig NS qwertylabs.au
dig A qwertylabs.au
dig MX qwertylabs.au
dig TXT qwertylabs.au
dig TXT default._domainkey.qwertylabs.au
dig TXT _dmarc.qwertylabs.au

If dig is unavailable use DNS Checker. The DKIM selector may differ; check cPanel for the actual name. SERVFAIL means lookup failed, not necessarily that the record is missing. NXDOMAIN means the queried name does not exist. Compare the public records with the owner-visible Zone Editor and stop before making changes.

Why QL cares: yesterday the nameservers pointed at a different VentraIP service; after correction and propagation, certificates and mail authentication recovered. Green ticks indicate consistent answers, not a guarantee that every service works.

HTTPS, certificates and redirects
HTTP / HTTPS
Hypertext Transfer Protocol carries web requests and responses. HTTPS wraps HTTP in TLS (Transport Layer Security), encrypting traffic and authenticating the server. A certificate binds the domain name to its public key and expires.
AutoSSL
cPanel's automatic certificate issuance/renewal system. It must establish control of the relevant hostnames.
301 redirect
A permanent HTTP response telling a browser to request a different URL. DNS does not redirect URLs; the web server does.
Canonical URL
The preferred public address. QL uses HTTPS, non-www, .au to avoid duplicate URLs.

Do it: cPanel → Security → SSL/TLS Status (or SSL/TLS Certificates → Status). Confirm certificates cover both root domains and both www names; record the expiry. Then Domains → Redirects and Domains → Force HTTPS Redirect (read-only). Check each URL below using a private browser window; note the final URL and whether there is a certificate warning.

curl -IL http://www.qwertylabs.com.au

The command shows response headers and follows redirects; look for Location: and final status. A temporary placeholder or missing website may be expected until upload. Do not mark the website itself live. If a certificate fails, stop; do not bypass the warning. Owner must approve any redirect changes.

Email: how messages reach the right inbox
SMTP — Simple Mail Transfer Protocol
Transfers outgoing email between clients and servers. Mail delivery logs record what happened at the server, not always at the inbox.
IMAP — Internet Message Access Protocol
Lets an email application read and synchronise messages kept on the server. Webmail is a browser interface to the same mailbox.
MX / local routing
MX tells other servers where to send mail; Local Mail Exchanger tells this cPanel account to accept mail for its hosted domain.
SPF — Sender Policy Framework
A TXT policy listing authorised sending systems for a domain. Receiving servers compare the sending host against that policy.
DKIM — DomainKeys Identified Mail
A digital signature attached to outgoing messages. Receivers look up the public key in DNS to check that the signed content was not altered. The private signing key stays on the server.
DMARC — Domain-based Message Authentication, Reporting and Conformance
Checks whether an authenticated SPF or DKIM domain aligns with the visible From domain; publishes a handling policy and optional reporting instructions. A valid record is not proof every message passes.

Do it: cPanel → Email → Email Routing: choose qwertylabs.au, verify Automatically Detect: Local. Email Deliverability → Manage main domain: confirm all three records are valid. Track Delivery: have the owner show only a synthetic message; compare sent time, recipient, result and bounce status. Owner can send and reply to a dummy test from an external inbox. Check spam if missing; view authentication headers for spf=pass, dkim=pass and dmarc=pass if available.

Do not regenerate DKIM, overwrite records or change mail routing when it is working. An old error can be cached; refresh and verify publicly. Stripe's own receipt delivery is separate from QL mailbox authentication.

Why we use several defences
SpamAssassin / Spam Filters
Scores incoming mail for spam signals; the threshold decides when to mark messages. Lower values catch more but may misclassify genuine mail. Spam Box quarantines rather than destroys it.
Catch-all / Default Address
Controls mail addressed to nonexistent accounts. Rejecting during SMTP stops junk addressed to guessed names without generating unnecessary bounce messages later.
2FA — Two-factor authentication
Adds a second proof of identity, beyond the password. The account owner holds the second factor and recovery methods.
Least privilege
Grant only the access needed for a task. A signed-in owner dashboard is not a student account. Use supervision or a separate restricted sandbox, never unattended live access.

Do it: In cPanel search Spam Filters, Default Address, and Email Deliverability. Compare actual settings with the summary cards; do not change them. Ask the owner to confirm VIPcontrol 2FA privately. Never share QR codes or keys.

Important: email spam filtering protects the inbox. It does not stop robots posting directly to a website form or abusing a confirmation email. That's a separate backend security problem covered later.

Stripe: how the objects fit together
Product
The service being sold, e.g. holiday camps. A product can have multiple prices without duplicating the service.
Price
Amount, currency and billing type. One-off prices are used here rather than subscriptions. Lookup keys are stable labels our server can use to find the appropriate Stripe price ID.
Customer
A stable Stripe billing customer represents the responsible adult or family account, not a separate Stripe customer for each child. QL’s own customer-facing records and invoice references are student-first. Link to a verified existing billing customer; never use a child’s name or an unverified email as a unique identifier.
Invoice / invoice item
An invoice is a request for payment. Items describe the charges and quantities. A draft is editable and must not be sent until availability and pricing are approved.
Payment Link
A reusable hosted checkout URL; useful for simple payments but not our primary custom booking flow. A payment link doesn't automatically know which dates or rates a family qualifies for.
Payout
Transfer from Stripe balance to QL's bank; separate from the customer's payment date.
Sandbox / live
Separate test and real environments, with separate API keys and objects. A sandbox payment is simulated. Never use live mode for an experiment.

Find it: With the owner, view Stripe Product catalogue → weekly classes and holiday camps → Prices; Settings → Branding, Customer emails, Payment methods and Billing → Invoices. Check the current mode before every action. Use only an authorised test workspace to create objects. The existing $10 sandbox link is optional for a demonstration.

Follow a booking from start to finish
  1. Parent enters one family booking, with one or more named students, their programme choices and one responsible billing contact. A review page shows what will be requested, not a confirmed booking.
  2. On final submit, the browser sends an HTTPS POST to QL's backend. The server authenticates anti-bot token, validates the data, recalculates price and saves a booking ID and pending state.
  3. Server saves each student enrolment separately under the shared family booking, creates or matches the authorised Stripe billing customer and creates one draft invoice. Combine identical charges into a single line with quantity. Save the Stripe invoice ID with the booking.
  4. Owner reviews availability, discounts, participant details and charges. Only authorised approval can reserve the place and finalise/send the invoice.
  5. Stripe hosts the payment page. Parent pays Stripe, not QL's form. Stripe sends receipt.
  6. Stripe notifies QL's backend using a webhook. Verify the signature and reconcile invoice status; update the booking to paid only when justified. Define cancellation, refunds and capacity release separately.

Possible states: received → pending_review → approved/invoiced → paid, plus declined, expired, cancelled or error. A draft is not a booking confirmation. Do not let the browser decide that payment succeeded.

Checkpoint: draw a box around the browser, the QL server and Stripe. Which data belongs in each box? Why should the browser never hold a Stripe secret?

Form protection: what, why and how
Turnstile
Cloudflare's bot challenge system. The browser receives a short-lived token; the backend sends it to Siteverify with a private secret. A widget alone does not secure a form. Test keys are available for development.
Honeypot
A field that normal users should never fill; some bots fill it anyway. Keep it out of keyboard navigation and assistive technology. Treat it as an extra signal rather than the sole defence.
Rate limiting
Limits the number of requests per time window. Prevents floods and repeated notification emails; don't rely on IP alone or block entire shared networks indiscriminately.
Server-side validation
Rejects malformed data or unauthorised choices even when someone skips the browser form. Allowlist dates, programme codes, sizes and formats.
CSRF / XSS / SQL injection
Cross-Site Request Forgery abuses a logged-in user's browser; protect approval with CSRF tokens and authentication. Cross-Site Scripting inserts executable content; render text safely. SQL injection manipulates database queries; use parameterised queries.

Test design: sketch the request pipeline: size limit → rate limit → validate required fields → verify bot token on server → price calculation → durable save → draft invoice → notification. Reject invalid token, invalid input and duplicates safely. For tests use Turnstile's official dummy keys; don't embed private credentials.

Don't send children's details in logs, screenshots or email alerts. Public response should reveal only an opaque booking reference and a clear status. Use generic errors for failures, with restricted diagnostic logs on the server.

Write and test a pricing function

Money is represented as integer cents so floating point rounding does not affect totals. For one child, the illustrative camp formula is first day 14,500 cents + (days − 1) × 13,000 cents + eligible extras 5,500 cents each (charging unit still needs approval).

Open a local JavaScript file or a browser console on a blank local page. Type this small prototype; explain each line:

function campTotal(days, extra = false) {
  if (!Number.isInteger(days) || days < 1 || days > 30)
    throw new Error('Invalid number of days');
  if (typeof extra !== 'boolean')
    throw new Error('Invalid extra');
  return 14500 + (days - 1) * 13000
    + (extra ? 5500 : 0);
}
console.assert(campTotal(1) === 14500);
console.assert(campTotal(4) === 53500);
console.assert(campTotal(4, true) === 59000);
try { campTotal(0); } catch (err) {
  console.log('Rejected:', err.message);
}

Extend it so it returns invoice lines, not just a number: description, quantity, lookup key, unit cents. For each student enrolment calculate charges from server-owned rules; group identical charges with the same programme, session/date scope, rate and description. Keep contributing student IDs in the internal allocation. Example: Jane and John, same returning weekly class, one line with quantity 2, unitCents 25500, totalCents 51000. If one pays standard rate and the other returning rate, use two lines ($270 + $255 = $525). Never infer eligibility from sibling status. One extra is illustrative only. Do not accept a customer's claimed total, arbitrary dates, rate or extra count as authoritative. Verify eligibility and selected dates on the server.

A local mock backend, step by step

An API (Application Programming Interface) is a defined way for programs to communicate. An HTTP endpoint is a URL that accepts requests; POST sends data to create an action; JSON (JavaScript Object Notation) is a text data format. A response may contain a status code (200/201 success, 400 invalid, 409 conflict, 429 too many requests, 500 server failure).

  1. Create a booking-mock.js file and your pricing function. Define the sibling test input above, plus a one-child camp day count. Use synthetic records only.
  2. Write createDraftMock(booking) that returns {status:'draft', lines:[...], totalCents:53500} from the pricing function. Validate first; never use an input price.
  3. Store results in a local Map keyed by booking ID. For a repeated identical request, return the same draft; reject a different payload using the same ID. This is an in-memory learning demo, not durable storage.
  4. Test success, invalid input, duplicate calls and consolidation: two student enrolments must remain distinct even when the invoice contains just one line. Then add a simple fake form and a review button if time allows. Show a result only after the mock returns success.
  5. Stretch: ask ChatGPT how to turn this into a local PHP endpoint, if PHP is installed. Use a loopback-only local server and dummy JSON. Do not deploy to public hosting yet.

For real deployment, we need an authenticated approval UI, durable database with unique booking IDs, server-owned allowed options, rate limits, secure secrets and appropriate privacy controls. The mock intentionally does none of that yet.

Making a Stripe draft safely

A secret API key authenticates a server to Stripe; anyone with it can use its permissions. A publishable key is different and is safe for approved client-side uses, but is not needed for our draft invoice flow. A restricted key limits allowed API operations. Only the owner creates, stores and revokes keys. Do not view, copy or paste keys into ChatGPT, JS or GitHub.
